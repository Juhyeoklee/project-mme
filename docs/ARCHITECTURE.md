# project-mme — 기술 구조

> 확정: 2026-07-27 / **스파이크 결과 반영 (§4)**
> 이직용 포트폴리오 사이드 프로젝트. 목표 포지션 **iOS 네이티브**.
> 어필 축은 **아키텍처 설계 역량**과 **AI를 활용한 개발 프로세스**.

---

## 1. 논지

> **계약은 하나, 런타임만 플랫폼별.**

스키마·기술자·알고리즘을 단일 진실 소스로 두고, 각 플랫폼은 그 계약을 자기 런타임으로 실행할 뿐이다.
같은 사진을 넣으면 iPhone에서든 Windows에서든 **같은 결과**가 나와야 한다.

개발 프로세스 쪽 논지가 하나 더 있다.

> **에이전트가 코드를 생산하는 시대에, 사람이 하는 일은 에이전트가 넘을 수 없는 경계를 설계하는 것이다.**

- **사람** — 도메인 모델과 모듈 경계, 의존성 규칙을 설계한다
- **에이전트** — 그 경계 안에서 구현·테스트·리팩터링을 한다
- **CI** — 경계 위반을 기계적으로 차단한다. 사람도 에이전트도 예외 없다

2026년에 "AI로 개발했습니다"는 차별점이 아니다. 차별점은 **에이전트의 생산 속도가 올라갈수록 아키텍처 경계가 유일한 품질 게이트가 된다**는 문제의식과, 그걸 실제로 강제하는 장치다.

---

## 2. 제품

**게임 스크린샷을 정리하고, 기억할 만한 순간을 기록으로 남기는 앱.**

지금은 카카오톡 안의 도구로 하고 있다. 불편한 건 **정리** 쪽이다.

### 유저가 지금 하는 일

1. 스크린샷 폴더를 쭉 훑는다 → **지겹다**
2. 그날 그 순간 사진들을 눈으로 묶는다 → **귀찮다**
3. 그중 잘 나온 것 몇 장 고른다 → **귀찮다**
4. 무슨 일이었는지 글로 쓴다 → **이건 재밌다. 건드리면 안 된다**

**1~3을 없애고 4만 남기는 게 전부다.**

### 순서가 중요하다

- 사람을 데려오는 건 **정리** (실제 불편함이 있다)
- 남게 만드는 건 **기록** (애착이 생긴다)

정리가 먼저 완성돼야 한다. 기록부터 만들면 "그래서 이걸 왜 써?"에 답할 수 없다.

### 첫 타깃

마비노기 모바일 커뮤니티. 개발자 본인이 하는 게임이라 첫 유저를 데려올 통로가 있다.
단, **구조는 게임 무관하게 만든다** (§3).

## 3. 소스 모델 — 게임이 이미 앨범을 만들어준다

| 플랫폼 | 저장 위치 |
|---|---|
| iOS / iPadOS | 사진 앱 안에 `Mabinogi Mobile` 앨범이 자동 생성 |
| Windows | `사진 > Mabinogi Mobile` 폴더 |
| Android | 유사할 것으로 추정 (미확인) |

요즘 모바일 게임의 일반적인 동작이다. → **"이름이 있는 컨테이너 하나 = 게임 하나"**로 끝난다.

- 유저가 앨범/폴더를 지정하면 그게 소스
- 게임별 하드코딩 0, **멀티 게임 지원이 공짜**
- 이미지 분류로 게임 스크린샷을 골라낼 필요 없음 — 원래 제일 어려운 문제였는데 사라졌다

```swift
// Domain — 플랫폼을 모른다
public protocol ScreenshotSource: Sendable {
    var id: SourceID { get }
    var displayName: String { get }
    func loadItems(since: Date?) async throws -> [ScreenshotRef]
    func observeChanges() -> AsyncStream<SourceChange>
}
```

| 플랫폼 | 구현 |
|---|---|
| iOS / iPadOS / macOS | `PhotoKitSource` — `PHAssetCollection` + `PHPhotoLibraryChangeObserver` |
| Windows / macOS 로컬 | `FileSystemSource` — 폴더 감시 |
| Web | `UploadSource` — 업로드 or File System Access API |

**이 추상화가 아키텍처의 심장이다.** 모듈 경계가 설계 취향이 아니라 문제 구조에서 나온다.

## 4. 스파이크 결과 — 검증된 사실

실제 스크린샷 **60장 / 12일치**로 검증했다 (2026-07-08 ~ 07-27, Windows 클라이언트).
아래는 추측이 아니라 측정값이다. 설계 판단의 근거이므로 README에도 그대로 쓴다.

### 4.1 HUD가 없다 — 최대 리스크 소멸

게임 내 촬영 모드로 찍으므로 **UI가 통째로 제거된 순수 장면**이다. 우하단 워터마크만 있고 크롭으로 제거된다.
"같은 게임이라 미니맵·스킬바가 항상 같은 자리에 있어 유사도가 무의미해질" 위험이 **존재하지 않는다.**

### 4.2 시간 간격 분포가 이봉이다 — 세션 경계가 자연히 존재

| 간격대 | 개수 |
|---|---|
| 1분 미만 | 23 |
| 1~5분 | 10 |
| **5~15분** | **1** ← 경계가 비어 있다 |
| 15분~1시간 | 7 |
| 1시간 이상 | 18 |

**임계값이 둔감하다.** 5분과 10분은 결과가 완전히 동일(27세션), 15분도 26세션.
→ 하이퍼파라미터 튜닝이 필요 없다. 기본값 **30분**으로 확정한다 (22세션).

### 4.3 날짜별 정리로는 부족하다

**12일 중 5일(42%)이 하루에 세션 2개 이상.** 7/26은 하루에 4세션 22장, 7/25도 4세션.

→ **MVP를 "날짜별"에서 "세션별"로 올린다.** 시간 기준이므로 난이도는 거의 오르지 않는다.

### 4.4 색감이 구조를 압도한다

| 기술자 | AUC | 1-NN 정확도 |
|---|---|---|
| **전역 HSV 히스토그램** | **0.844** | 73% |
| 격자 HSV 8×8 | 0.843 | 75% |
| 격자 HSV 4×4 | 0.824 | 75% |
| dHash | 0.712 | 52% |
| 축소판 32×32 상관 | 0.688 | 60% |
| pHash | 0.644 | 52% |

장소마다 색조가 확연히 다르고(밝은 초원 vs 어두운 실내), 구도는 카메라가 계속 움직여 일관성이 없다.
**격자로 나눠도 전역과 차이가 없다** — 구도 정보가 실질적으로 도움이 안 된다는 뜻이다.

### 4.5 시각 유사도는 시간을 대체할 수 없다 — 다른 축이다

HSV로 군집하면 35~46개가 나오고 시간 세션(22개)과 **ARI 0.23~0.44**에 머문다.
그리고 다른 세션인데 같은 세션보다 더 비슷한 쌍이 실재한다(같은 장소를 다른 날 촬영).

→ 역할 분담이 확정된다. **시간 = 1차 축, 시각 = 2차 축** (§5).

### 4.6 근접중복이 실재한다 — 베스트컷 기능의 근거

pHash 거리 0.15 미만인 쌍이 **9쌍**. 2~18초 차이로 연사한 거의 같은 컷이다.
그중 **5쌍이 12장 세션 하나에 몰려** 있다.

→ v3에서 뺐던 **베스트컷 골라주기를 되살린다.** pHash로 되므로 비용이 거의 0이고,
§2의 유저 워크플로우 3단계("잘 나온 것 고르기")를 직접 없앤다.

### 4.7 구현 세부 두 가지

**파일명 타임스탬프를 1차 소스로 쓴다.**
형식은 `MabinogiMobile_YYYYMMDDHHMMSSff.png`이고 mtime과 **1초 이내로 일치하며 더 정밀**하다(1/100초).
PNG라 EXIF를 신뢰할 수 없고, 파일을 복사·이동하면 mtime은 바뀌지만 파일명은 유지된다.
→ **파일명 파싱 → 실패 시 EXIF → 실패 시 mtime** 순서로 폴백한다.

**해상도가 균일하지 않다.** 60장에서 **7종**이 나왔다.
`1233×953`(20장), `1243×954`(19장), `1235×954`(9장), `1249×960`(6장), **`708×954`(4장, 세로)**, `1250×960`, `1216×953`.
촬영 모드에서 비율을 바꿀 수 있는 것으로 보인다.
→ 기술자 계산 전 정규화가 필수이고, 그리드 레이아웃도 종횡비 혼재를 전제로 설계한다.

## 5. 그룹핑 설계 — 시간이 1차, 시각이 2차

§4.5의 측정 결과에 따른 확정 설계다.

| 축 | 하는 일 | 방법 | 비용 |
|---|---|---|---|
| **1차 · 시간** | 세션 나누기 | 간격 30분 초과 시 분할 | 무료 |
| **2차 · 시각** | 세션 안 근접중복 묶기 | pHash 거리 < 0.15 | 매우 낮음 |
| **2차 · 시각** | 세션 넘어 같은 장소 찾기 | HSV 히스토그램 거리 | 낮음 |

**시각 유사도로 세션을 나누지 않는다.** 시간이 이미 더 잘 하고, 둘은 다른 것을 본다.

### 이 설계의 이득

- **1차 축만으로 제품이 완성된다.** 2차 축은 전부 부가 기능이므로 실패해도 손실이 없다
- 임계값 튜닝이 필요 없다 (§4.2)
- 신경망이 필요 없다 (§6)

## 6. 크로스플랫폼 기술자 공유 — 모델이 아니라 스펙

§4.4·4.6에서 **고전 기술자만으로 충분함이 확인**됐다. 이게 구조를 크게 단순화한다.

```
이전 계획                          확정
─────────────────────────────      ────────────────────────────
임베딩 모델 아티팩트                contracts/descriptor.md
  ├─ Core ML 변환                    (스펙 하나. 언어별 구현)
  ├─ ONNX Web 변환
  └─ ONNX Mobile 변환
tools/modelgen                     (삭제)
Git LFS 또는 다운로드 파이프라인      (삭제)
```

pHash와 HSV 히스토그램은 **DCT와 히스토그램뿐인 순수 산술**이다.
따라서 Swift와 TypeScript 구현이 **비트 단위로 동일**할 수 있다.

사라진 것: 모델 배포, Core ML 변환, ONNX 런타임 의존, 앱 번들 증가, 웹 모델 다운로드, `modelgen` 툴, Git LFS.

### 골든 테스트는 오히려 강해진다

`contracts/fixtures/`에 입력 이미지와 기대 기술자 값을 두고, **Swift 구현과 TS 구현이 비트 단위로 같은지** CI에서 검증한다.
신경망이면 부동소수 오차를 허용해야 했지만, 순수 산술이므로 **완전 일치를 요구할 수 있다.**

`ArchLint`가 Swift 내부 경계를 지킨다면, 골든 테스트는 **언어 간 경계**를 지킨다.

### 신경망은 뒤로 미룬다

AUC 0.844를 CLIP 계열로 0.9대까지 올릴 여지는 있다. 다만 **필요성이 증명된 뒤에** 도입한다.
포트폴리오로도 이 순서가 낫다 — *"고전 기술자로 먼저 검증하고, 신경망은 근거가 생긴 뒤 도입했다"*가 성숙한 판단으로 읽힌다.
도입할 때도 §6의 구조(스펙 = 계약)는 그대로 유지되고, 구현체만 바뀐다.

## 7. 2층 구조 — 로컬과 원격

**모든 스크린샷을 서버에 올리지 않는다. 유저가 기록으로 남기기로 한 것만 올라간다.**

| | 로컬 층 | 원격 층 |
|---|---|---|
| 대상 | 스크린샷 **전량** | 유저가 **고른 것만** |
| 역할 | 정리·탐색·그룹핑 | 기록 보관·동기화·공유 |
| 저장 | 사진앱 참조 + 로컬 DB | Supabase (Postgres + Storage) |
| 오프라인 | 완전 동작 | 불필요 |
| 원본 이동 | **없음** | 리사이즈·압축 후 업로드 |

### 동시에 푸는 것 세 가지

1. **비용** — 전량 업로드는 무료 티어를 첫 주에 터뜨린다. 기록당 3~5장이면 감당된다.
2. **아키텍처 경계** — Domain/Data 분리가 제품 요구와 겹친다. 억지 레이어가 아니다.
3. **프라이버시 서사** — *"스크린샷은 기기를 떠나지 않습니다. 올리기로 한 기록만 올라갑니다."*

### 제품 루프

```
정리(로컬) → 기록(로컬) → 게시(서버) → 웹 링크 공유 → 친구 유입
```

카톡에 올리는 행위를 **공유 링크 하나**로 대체한다. 그 링크가 그대로 유입 경로가 된다.

## 8. 모노레포

### 왜 필수인가

§1의 명제가 "계약은 하나"인데, 레포가 갈라지면 **그 계약이 지켜지는지 증명할 방법이 없다.**
스키마를 고치고 웹만 반영한 상태가 커밋될 수 있다. 한 레포에 있어야 CI가 한 번에 잡는다.

**모노레포는 편의가 아니라 논지의 필수 조건이다.**

```
project-mme/
├── AGENTS.md
├── docs/adr/
│
├── contracts/                 ★ 단일 진실 소스
│   ├── schema/                  Postgres 마이그레이션
│   ├── descriptor.md            pHash · HSV 히스토그램 스펙
│   ├── clustering.md            세션 분할 · 근접중복 묶기 스펙
│   └── fixtures/                골든 테스트 데이터 (입력 → 기대 기술자값)
│
├── apps/
│   ├── apple/                   Tuist 워크스페이스 (iOS/iPadOS/macOS)
│   ├── web/                     React
│   ├── desktop/                 Tauri (web 참조)
│   └── android/                 후순위
│
├── packages/
│   ├── core/                    도메인 로직 TS 구현
│   └── api-types/               supabase gen types 출력
│
├── tools/
│   ├── archlint/                Swift 의존성 규칙 검증
│   └── schemagen/               Postgres → Swift 타입
│
└── supabase/
```

### 도구는 최소로

**pnpm workspaces (JS) + Tuist (Swift), 최상위엔 얇은 태스크 러너 하나.**

**Bazel·Nx로 통합하려는 유혹을 이긴다.** 폴리글랏 모노레포의 정석처럼 보이지만 Swift/Xcode를 Bazel에 물리는 건 그것만으로 몇 주짜리다.

### 조심할 것

| | 문제 | 대응 |
|---|---|---|
| **CI 비용** | macOS 러너는 Linux의 10배로 소모. 웹 파일 하나 고쳐도 Apple 빌드가 돌면 무료 한도가 며칠 만에 날아감 | **path filter를 0주차에 세팅.** 나중에 하면 늦다 |
| **Xcode 인덱싱** | `node_modules`, Rust `target/`을 긁으며 느려짐 | Tuist 프로젝트를 `apps/apple/`에 격리 |

모델 아티팩트 문제는 §6으로 소멸했다.

## 9. 플랫폼 역할 분담

각 플랫폼은 **별개의 네이티브 프로그램**이다. UI는 공유하지 않는다. 공유하는 건 `contracts/`뿐.

| 플랫폼 | 구현 | 깊이 | 역할 |
|---|---|---|---|
| **iOS / iPadOS** | SwiftUI | **깊게** | 주 사용처 |
| **macOS** | 같은 SwiftUI 코드베이스 | 중간 | 대량 정리 + 키보드로 글쓰기 |
| **Web** | React | 효율 | **공유 기록 뷰어(로그인 불필요)** + Windows 클라이언트 |
| **Windows** | Web + Tauri | 효율 | 게임 폴더 감시. **주 촬영 환경이므로 실사용 비중이 높다** |
| **Android** | 웹 자산 재활용 | 최소 | 우선순위 낮음 |

**React Native는 채택하지 않는다.** 최대 가치가 iOS+Android 코드 공유인데 iOS는 네이티브로 깊게 간다.

**macOS를 넣는 이유** — Mac에서 게임을 하지 않으므로 진입점은 아니다. 그럼에도 넣는 건 (a) 수백 장 훑기는 큰 화면이 압도적이고 (b) 글쓰기는 키보드가 편하며 (c) SwiftUI 멀티플랫폼이라 추가 비용이 낮기 때문이다.

### WebView 정책

> **WebView는 "웹에 이미 존재해야 하는 화면"을 재사용할 때만 쓴다.
> 리소스를 아끼려고 네이티브 화면을 웹으로 만들지 않는다.**

| 화면 | 판단 | 이유 |
|---|---|---|
| 온보딩 (앨범 선택) | 네이티브 | 권한 요청, 앨범 열거 |
| **라이브러리 그리드** | **네이티브 필수** | 수천 장 스크롤. `PHAsset` 썸네일 로드·캐시 |
| **세션 확인·편집** | **네이티브 필수** | 다중 선택, 드래그 제스처 |
| **기록 에디터** | **네이티브 필수** | 유저가 가장 오래 머무는 화면. 인터랙션 품질 = 제품 품질 |
| 내 기록 목록 | 네이티브 | 단순함 |
| **공유된 기록 보기** | **WebView** | 웹에 반드시 있어야 하는 화면 (§7) |
| 약관·정책·공지 | WebView / Safari | 논쟁거리 아님 |

**공유 기록 뷰어에서 WebView는 절감 수단이 아니라 일관성 확보 수단이다.**

### 왜 더 넓게 쓰지 않는가

1. **뺄 수 있는 화면이 2개뿐이다.** 그리드를 WebView로 만들면 사진을 파일 URL/base64로 넘겨야 하고 수천 장 스크롤에서 무너진다.
2. **브릿지 고정비용이 절감분을 먹는다.** Swift↔JS 메시지, 인증 토큰 공유, 네비게이션 상태 동기화, 다크모드·폰트·Safe Area 동기화, 오프라인 처리, **디자인 시스템 이중 관리**.
3. **포트폴리오 목적과 충돌한다.** 화면 절반이 WebView면 SwiftUI 역량의 증거가 아니라 반대로 읽힌다.
4. **심사 리스크.** App Store Guideline 4.2(Minimum Functionality).

## 10. 데이터 계약

**Supabase의 Postgres 스키마가 계약이다.**

```
Postgres 스키마
    ├─→ TypeScript 타입   supabase gen types typescript   (공식 도구)
    └─→ Swift 타입        tools/schemagen                 (직접 제작)
```

스키마를 고치면 **두 클라이언트가 동시에 컴파일 에러를 낸다.**

Swift 코드젠은 Supabase가 제공하지 않으므로 직접 만든다. 테이블 메타데이터를 읽어 `Codable` 구조체를 뽑는 수준. **범용 도구로 만들지 않는다.**

| 테이블 | 내용 |
|---|---|
| `profiles` | 유저 |
| `entries` | 기록 — 제목, 본문, 발생일시, 공개여부, 공유 슬러그 |
| `entry_images` | 첨부 이미지 — Storage 경로, 순서, 캡션 |
| `games` | 게임 메타. 유저가 추가 가능 |

**로컬 전용 데이터는 서버에 없다** — 소스 등록 정보, 세션 분할 결과, 유저의 그룹 수정, 기술자 캐시.

RLS로 본인 데이터만 접근하게 하고, `is_public = true`인 `entries`만 익명 읽기를 허용한다. 웹 뷰어가 로그인 없이 동작하는 근거.

## 12. TCA — 부분 도입

기준은 *"되돌릴 수 있는 복잡한 상태 전이가 있는 화면이 몇 개인가"*였다.
**기록 에디터**(사진 붙였다 떼기, 취소, 되돌리기)와 **다중 선택·세션 편집** 두 곳이다.

### 결정: 기록 에디터만 TCA. 나머지는 `@Observable`.

1. **완주 가능성** — 사이드 프로젝트는 완성돼야 포트폴리오가 된다. TCA 2.0이 유료 베타라 지금 짜는 1.26 문법은 `@Feature` 매크로 기반으로 곧 바뀐다.
2. **오히려 더 강한 포트폴리오** — 같은 앱에 두 방식이 나란히 있으면 실제 코드로 비교를 말할 수 있다. *"TCA 써봤습니다"*보다 *"이 화면은 TCA로, 저 화면은 아닌 이유가 이겁니다"*가 훨씬 강하다.

ADR로 비교 근거를 남긴다.

## 13. Apple 모듈 그래프

```
apps/apple/
├── Tuist/ProjectDescriptionHelpers/    # 레이어 정의 + 허용 의존성
└── Projects/
    ├── App/                             # 조립만
    ├── Feature/
    │   ├── Library/                     # 스크린샷 탐색·정리
    │   ├── SessionEditor/               # 세션 확인·편집
    │   ├── EntryEditor/                 # 기록 에디터 ← TCA
    │   └── Settings/
    ├── Domain/                          # 순수 Swift. Foundation만
    │   ├── Entity/                      # Screenshot, Session, Entry, Game
    │   ├── Grouping/                    # 세션 분할 · 근접중복 묶기 (순수 로직)
    │   └── Interface/                   # ScreenshotSource, EntryRepository,
    │                                    #   ImageDescriptorComputing
    ├── Data/
    │   ├── PhotoKitSource/
    │   ├── FileSystemSource/
    │   ├── LocalStore/                  # SwiftData
    │   ├── DescriptorKit/               # pHash · HSV (vImage/Accelerate)
    │   └── SupabaseClient/              # 3단계부터
    └── Core/
        ├── DesignSystem/
        └── CoreKit/
```

`Domain/Grouping`이 순수 로직인 게 중요하다. `contracts/clustering.md` 스펙의 Swift 구현이며,
`packages/core`의 TS 구현과 골든 테스트로 대조된다(§6).

### 의존성 규칙

| 레이어 | import 가능 | 금지 |
|---|---|---|
| `App` | 전부 | — |
| `Feature` | `Domain`, `Core` | **`Data`, 다른 `Feature`** |
| `Domain` | — (Foundation만) | 전부 |
| `Data` | `Domain`, `Core` | `Feature` |
| `Core` | — | 전부 |

- **`Feature`가 `Data`를 모르는 게 핵심.** Feature는 `Domain/Interface` 프로토콜만 알고 구현체 주입은 `App`이 한다. → 기술자 계산·Supabase를 스텁으로 갈아끼우고 Feature 테스트를 결정론적으로 돌린다.
- **`Feature` 간 직접 참조 금지.** 화면 전환은 부모가 조립한다.

### 강제 3단

1. **빌드** — Tuist에서 의존성을 안 걸어주면 컴파일 실패
2. **`tuist inspect implicit-imports`** — 우회 import 검출
3. **`ArchLint`** — 그래프를 규칙표와 대조. 전이 의존과 순환을 잡는다

Tuist에는 레이어 규칙 선언 기능이 없다(`inspect`는 미선언/미사용 import만 본다). 그래서 `ArchLint`를 직접 만든다.
**아키텍처를 설계했다는 말은 흔하고, 규칙을 기계가 강제하게 만든 사례는 드물다.**
범위는 규칙표 대조 + 순환 검출까지. **범용 도구로 만들지 않는다.**

## 14. AI 개발 프로세스

어필 축이 "개발 프로세스"인 만큼 결과물은 앱만이 아니라 **레포 그 자체**다.
(제품 안에는 AI 모델이 없다 — §6. AI는 **개발 도구로만** 쓴다.)

### Xcode ↔ Claude Code 연결

1. Xcode → Settings → **Intelligence** → **"Allow external agents to use Xcode tools"** 켜기
2. `claude mcp add --transport stdio xcode -- xcrun mcpbridge`
3. **에이전트 실행 전에 Xcode에서 프로젝트를 열어둬야 한다** — 브리지가 실행 중인 인스턴스에 붙는 구조

에이전트가 컴파일러 진단, 빌드·테스트 실행, SwiftUI 프리뷰 렌더링, 시뮬레이터 조작에 직접 접근한다.
→ **에이전트가 자기 작업을 스스로 검증하는 루프**가 닫힌다.

### 레포에 남길 것

| 파일 | 역할 |
|---|---|
| `AGENTS.md` | 아키텍처 규칙·레이어표·금지사항. Apple이 공식 문서에서 이 파일명을 권장한다 |
| `.claude/skills/add-feature-module/` | Tuist 스캐폴딩 + 화면 골격 + 테스트 골격 |
| `.claude/skills/add-dependency/` | Domain 프로토콜 + Data 구현 + 테스트 스텁 세트 |
| `docs/adr/` | 결정 기록 |

Xcode 내장 Agent Skills도 내보내 재사용한다. **export 문법은 `xcrun agent skills export --help`로 먼저 확인할 것** — 애플 공식 문서에 없고 커뮤니티에 두 형태가 돈다.

### CI = 에이전트의 상한선

```
1. tuist inspect implicit-imports
2. swift run ArchLint
3. swift build          (Swift 6 strict concurrency)
4. swift test           (네트워크 없이 결정론적)
5. 골든 테스트           (Swift 기술자값 == TS 기술자값, 비트 단위 일치)
```

**사람이 짜든 에이전트가 짜든 동일하게 적용된다.** 이 대칭성이 §1 명제의 실행이다.

| 단계 | 범위 | 서버 | 완료 기준 |
|---|---|---|---|
| **0** | 모노레포 골격 | — | `contracts/` + Tuist 그래프 + `ArchLint` + CI path filter + `AGENTS.md` + Xcode MCP |
| **1** | iOS/iPadOS — 앨범 지정, **세션별 정리** | 없음 | 내 사진으로 실제로 쓸 만함. macOS는 빌드만 |

| **3** | Supabase — 계정, 게시, 웹 뷰어 | 등장 | 공유 링크가 브라우저에서 열림 |
| **4** | macOS 다듬기, Windows Tauri | | Windows는 주 촬영 환경이라 실사용 비중이 높다 |

**1단계가 "날짜별"에서 "세션별"로 올라갔다** (§4.3). 시간 기준이라 난이도는 거의 오르지 않는다.

**단계마다 실제 쓸 수 있는 상태를 유지한다.** 3단계에 처음 실행되는 프로젝트는 계획 실패다.

공유 기록 뷰어를 WebView로 쓰기로 했으므로(§9), 웹 작업 중 **그 한 화면만 3단계로 당겨진다.**

| **CloudKit** | Supabase와 역할 중복. 동기화 소스가 둘이면 반드시 사고 난다 |
| **GRDB** | 벡터 검색이 사라져 SQLite 제어권이 필요 없어짐 |
| **TCA 전면 도입** | 사이드 프로젝트 완주 가능성. 부분 도입이 오히려 강한 카드 |
| **TCA 2.0** | Point-Free Max 유료 베타. 공개 태그 없음 |
| **Xcode 27** | 7월 현재 베타. 배포 타깃 최소값 상승으로 구형 SPM 패키지가 깨지는 이슈가 열려 있음(Tuist #11163). 에이전트·MCP는 26.3부터 지원되므로 베타 갈 이유 없음 |
| **Bazel · Nx** | Swift/Xcode를 물리는 것만으로 몇 주짜리. 사이드 프로젝트를 죽이는 가장 흔한 방식 |

| **스크린샷 전량 서버 업로드** | 비용·프라이버시. §7 |
| **Windows용 iCloud를 동기화 파이프로** | 검증 불확실 + Windows 유저에게 "iCloud 깔고 로그인"은 이탈 지점 |

### 아이디어 디벨롭에서 풀어야 할 핵심 난제

**자동으로 묶어준 세션을 유저가 어떻게 고치는가.**

이게 이 앱 UX의 중심 문제다. 자동화가 틀렸을 때 고치는 비용이 크면 자동화 자체가 부담이 된다.
"묶기"는 알고리즘 문제지만 **"묶은 걸 쪼개고 합치기"는 인터랙션 문제**고, 후자가 훨씬 어렵다.

§4의 실측이 구체적인 하위 질문을 만들어준다.

- **1장 세션 6개를 어떻게 표현하나** (22세션 중 27%). 세션으로 보여주면 노이즈, 낱장으로 빼면 일관성이 깨진다
- **12장 세션(7/26 18:05)처럼 큰 세션을 어떻게 보여주나.** 장수가 곧 중요도 신호인가?
- **근접중복 9쌍을 어떻게 접나.** 자동으로 접고 대표 1장만? 유저가 펼칠 수 있게?
- 세션의 표현 단위 — 날짜 아래 세션? 세션 평면? 계층?
- 세션 분할·기술자 계산을 언제 돌리나 — 임포트 시점? 조회 시점? 백그라운드?
- **유저 수정을 어떻게 보존하나** — 재실행하면 수정이 날아가면 안 된다
- 세션에서 기록으로 넘어가는 동선
- 기록 카드 내보내기 형태 (카톡·인스타 공유용)
- 종횡비 혼재(§4.7)를 그리드에서 어떻게 다루나

### 참고

- **§4는 측정값이다.** 추측과 구분해서 다룰 것. 여기 어긋나는 설계는 틀린 설계다
- 결정 근거는 §18에 모여 있다. 뒤집으려면 그 근거를 먼저 반박해야 한다
- 범위 확장은 ADR을 쓰게 강제한다
- 판단 기준 두 개: **"웹에 이미 존재해야 하는 화면만 WebView"**(§9), **"되돌릴 수 있는 복잡한 상태 전이가 있으면 TCA"**(§12)
- 스파이크 코드와 리포트는 `spike/`에 있다 — 재현 가능하다
