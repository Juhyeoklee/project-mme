# 모아노기 — 프로젝트 의도

> 저장소 이름 `project-mme`는 코드명이다.
>
> **이 문서는 설계 명세가 아니다.** 담는 것은 세 가지뿐이다 —
> **무엇을 만들고 싶은가 · 무엇을 보여주고 싶은가 · 무엇을 하지 않기로 했는가.**
>
> 기능 정의 · 화면 IA · 데이터 모델 · 모듈 구조는 여기 없고 **이 저장소에도 두지 않는다.**
> 구현과 함께 낡는 명세를 남기면 코드보다 문서가 먼저 눈에 띈다.

---

## 1. 이 프로젝트로 증명하려는 것

이직용 포트폴리오다. 목표 포지션은 **iOS 네이티브**.
따라서 성공 조건은 "잘 팔리는 앱"이 아니라 **"이 사람이 무엇을 할 수 있는지 보이는 앱"**이다.

증명하려는 것은 두 가지다.

**하나 — 아키텍처 설계 역량.**
경계를 말로 주장하지 않고 기계가 강제하게 만든다. 그리고 그 경계가 설계 취향이 아니라 문제 구조에서 나왔음을 보인다.

**둘 — AI를 활용한 개발 역량.**

> 에이전트가 코드를 생산하는 시대에, 사람이 하는 일은 에이전트가 넘을 수 없는 경계를 설계하는 것이다.

2026년에 "AI로 개발했습니다"는 차별점이 아니다. 차별점은 **에이전트의 생산 속도가 올라갈수록 아키텍처 경계가 유일한 품질 게이트가 된다**는 문제의식과, 그걸 실제로 강제하는 장치다.

그리고 이건 **사이드 프로젝트**다. **완성돼야 포트폴리오가 된다.** 모든 판단에 완주 가능성을 넣는다.

---

## 2. 제품

**게임 스크린샷을 정리하고, 기억할 만한 순간을 기록으로 남기는 앱.**

지금은 카카오톡 안의 도구로 하고 있다. 불편한 건 **정리** 쪽이다.

내가 지금 하는 일은 이 네 단계다.

1. 스크린샷 폴더를 쭉 훑는다 → **지겹다**
2. 그날 그 순간 사진들을 눈으로 묶는다 → **귀찮다**
3. 그중 잘 나온 것 몇 장 고른다 → **귀찮다**
4. 무슨 일이었는지 글로 쓴다 → **이건 재밌다. 건드리면 안 된다**

**1~3을 없애고 4만 남기는 게 전부다.**

순서가 중요하다. 사람을 데려오는 건 **정리**(실제 불편함이 있다), 남게 만드는 건 **기록**(애착이 생긴다).
정리가 먼저 완성돼야 한다.

**첫 타깃은 마비노기 모바일 커뮤니티.** 본인이 하는 게임이라 첫 유저를 데려올 통로가 있다.
단, 특정 게임에 종속되지 않게 만든다.

기록은 남들에게 보여줄 수 있어야 한다. 지금 카톡에 올리는 행위가 그거니까.
그래서 **공유 가능한 기록**이 제품의 한 축이고, 여기서 서버가 필요해진다.

## 3. 써보고 싶은 것과 그 이유

이 프로젝트를 하는 실제 동기다. **각 항목이 "무엇을 보여줄 수 있는가"에 답해야 채택된다.**

### 전제 — 정하고 시작한 것

이 넷은 심사 대상이 아니다. 이 프로젝트를 하는 이유에 포함된다.

| | 왜 | 보여줄 수 있는 것 | 관련 ADR |
|---|---|---|---|
| **SwiftUI 멀티플랫폼** | iOS·iPadOS·macOS를 한 코드베이스로 | 플랫폼별 적응 설계, SwiftUI 깊이 | |
| **모듈 경계를 기계로 강제** | 말이 아니라 CI로 증명 | 아키텍처 설계 역량 (주 무기) | `0001` |
| **에이전트 개발 워크플로우** | Xcode MCP + Claude Code로 검증 루프 닫기 | AI 활용 역량, 2026년의 실제 개발 방식 | |
| **플랫폼 간 계약 공유** | 플랫폼이 달라도 같은 결과가 나오게 | 시스템 경계 설계 | `0001` |

### 후보 — 필요성이 확인되면 채택한다

**써보고 싶다는 것만으로는 채택 근거가 아니다.** 각각은 근거가 생긴 시점에 ADR로 판정된다. **`결정` 칸이 비어 있으면 아직 근거가 안 생긴 것이다.**

| | 왜 | 보여줄 수 있는 것 | 결정 |
|---|---|---|---|
| **의존성 규칙 검증기** (직접 만든 도구) | 컴파일러가 못 막는 위반이 셋 실재한다 | 문제 해결 방식 | `0001` 채택 |
| **TCA** | 쓸지 말지를 근거로 판단하고 싶다 | 판단력 (무지성 도입보다 강함) | |
| **Supabase** | 서버까지 혼자 세워보기 | 풀스택 감각, 권한 설계 | |
| **웹 자산을 네이티브 셸에 담기** (Windows · Android) | 같은 노력으로 두 플랫폼을 덮기 | 효율 판단, 멀티플랫폼 실행력 | |
| **타입 코드젠** (직접 만든 도구) | 없는 건 만들어서 쓴다 | 문제 해결 방식 | |

AI를 제품 기능에 쓸지도 여기서 정하지 않는다. **정말 필요한 자리가 있는지는 근거를 보고 판단한다.**

## 4. 플랫폼 역할 분담

### 원칙 하나

> **모든 플랫폼은 네이티브 앱이다. 웹 자산은 그 안에서 재사용된다.
> 플랫폼마다 다른 것은 재사용 비중뿐이다.**

브라우저에 올린 웹앱을 "앱"이라고 부르며 끝내지 않는다. 어느 플랫폼이든 설치되고, 그 OS의 생명주기와 파일 접근을 쓰고, 그 OS답게 동작하는 프로그램이어야 한다. 그게 **본체**다.
그 위에서, 네이티브일 이유가 없는 화면은 웹 자산을 담아 쓴다.

Apple 생태계는 **재사용 비중을 최소로** 두고 깊게 판다 — 포트폴리오의 주 무대이기 때문이다.
Windows와 Android는 **재사용 비중을 최대로** 둔다 — 같은 노력으로 두 플랫폼을 덮는 게 합리적이기 때문이다.

| 플랫폼 | 본체 | 웹 자산 재사용 | 비고 |
|---|---|---|---|
| **iOS / iPadOS** | SwiftUI 네이티브 | **최소** | 주 사용처. 가장 깊게 |
| **macOS** | 같은 SwiftUI 코드베이스 | 최소 | 큰 화면 정리 + 키보드로 글쓰기 |
| **Windows** | 네이티브 셸 (Tauri 등) | **최대** | **주 촬영 환경이라 실사용 비중이 높다** |
| **Android** | 네이티브 셸 | **최대** | **PWA로 끝내지 않는다.** 설치되는 앱까지 만든다 |
| **Web** | 브라우저 | — | 공유 기록 뷰어(로그인 불필요) + 위 두 셸의 재료 |

**macOS를 넣는 이유** — Mac에서 게임을 하지 않으므로 진입점은 아니다. 그럼에도 넣는 건
(a) 수백 장 훑기는 큰 화면이 압도적이고 (b) 글쓰기는 키보드가 편하며 (c) 추가 비용이 낮기 때문이다.

**주 촬영 환경은 Windows PC와 iPhone/iPad다.** Mac이 아니다.

**Android를 웹으로 때우지 않는 이유** — 스크린샷은 기기의 특정 폴더/앨범에 쌓인다. 브라우저에 갇힌 웹앱은
그 폴더를 지속적으로 읽을 수도, 새 사진이 생겼을 때 알 수도 없다. 즉 **이 제품의 핵심 기능이 네이티브 접근을 요구한다.**
Windows에서 Tauri를 쓰는 이유도 같다 — 웹 화면을 담기 위해서가 아니라 **폴더를 감시하기 위해서**다.

## 5. 채택하지 않은 것

**제품 방향 · 플랫폼 전략 · 툴체인 수준의 결정만 여기 있다.**
기능·알고리즘·화면에 관한 판단은 여기 없다.

| 탈락 | 근거 |
|---|---|
| **게임 데이터 헬퍼 앱** (원래 아이디어) | 데이터 확보 비용이 개발 비용을 초과한다. 게임사 API 정책에 프로젝트 수명이 종속된다 |
| **React Native** | 두 가지 이유다. (a) 최대 가치가 iOS+Android 코드 공유인데 iOS는 네이티브로 깊게 간다 — Android 하나 때문에 짊어질 짐이 아니다. (b) **RN은 "웹 자산 재사용"이 아니다.** React 컴포넌트를 RN 컴포넌트로 다시 짜야 하므로 웹 화면을 그대로 담을 수 없다. §4의 재사용 전략과 방향이 맞지 않는다. (딸린 판단: Nitro Modules는 Swift 경로에 컴파일러 크래시·codegen 버그·Swift 6 strict concurrency 미지원이 열려 있어 애초에 선택지가 아니었다) |
| **PWA로 Android·Windows 때우기** | 브라우저에 갇힌 웹앱은 스크린샷 폴더를 지속적으로 읽거나 새 사진을 감지할 수 없다. **이 제품의 핵심 기능이 네이티브 접근을 요구한다.** §4 |
| **Apple에서 UI 대부분을 WebView로** | 아끼려고 네이티브 화면을 웹으로 만들면 브릿지 고정비용(인증 공유, 네비게이션 상태 동기화, 디자인 시스템 이중 관리)이 절감분을 먹는다. 무엇보다 화면 절반이 WebView면 SwiftUI 역량의 증거가 아니라 반대로 읽힌다. Apple에서는 **웹에 이미 존재해야 하는 화면만** 재사용한다 (Windows·Android는 반대로 최대한 재사용한다 — §4) |
| **Windows용 iCloud를 동기화 파이프로** | 검증이 불확실하고, Windows 유저에게 "iCloud 깔고 로그인"은 이탈 지점이다 |
| **Xcode 27** | 2026-07 현재 베타. 배포 타깃 최소값 상승으로 구형 SPM 패키지가 깨지는 이슈가 열려 있다(Tuist #11163). 에이전트·MCP는 Xcode 26.3부터 지원되므로 베타로 갈 이유가 없다 |
| **Bazel · Nx** | 폴리글랏 모노레포의 정석처럼 보이지만 Swift/Xcode를 물리는 것만으로 몇 주짜리다. 사이드 프로젝트를 죽이는 흔한 방식이다. 각 생태계는 자기 도구를 쓰고 최상위는 호출만 한다 |

**면접에서는 채택한 것보다 이쪽이 강한 카드다.** 각각 ADR로 남긴다.
