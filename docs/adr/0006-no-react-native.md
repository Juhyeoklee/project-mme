# 0006 — React Native를 쓰지 않는다

> 상태: **확정** · 결정 2026-07 (`WHY.md` 작성기) · 기록 2026-08-05
> `WHY.md` §5 탈락 표의 ADR 기록이다 — 새 논증이 아니라 §4·§5에 이미 적힌 것을 옮겨 닫는다.

## 맥락

플랫폼 다섯(iOS·iPadOS·macOS·Windows·Android)을 혼자 덮어야 한다. 크로스플랫폼
프레임워크의 표준 답이 React Native고, 그 최대 가치는 iOS+Android 코드 공유다.

그런데 이 프로젝트의 전제 둘이 그 가치와 부딪힌다. **하나** — 목표가 iOS 네이티브
포트폴리오라, Apple 쪽을 SwiftUI로 깊게 파는 것이 프로젝트의 존재 이유다(`WHY.md` §1).
**둘** — 플랫폼 전략이 *"모든 플랫폼은 네이티브 앱이고, 웹 자산이 그 안에서 재사용된다"*
로 이미 섰다(§4). 재사용의 단위는 웹 화면이다.

## 결정

**React Native를 쓰지 않는다.** Apple은 SwiftUI 네이티브, Windows·Android는
네이티브 셸에 웹 자산을 최대로 담는다(§4).

## 근거

**1. 최대 가치가 이 프로젝트에서 0이다.** RN의 값은 iOS+Android 코드 공유인데,
iOS는 네이티브로 깊게 가기로 §1이 이미 정했다. 그 축이 빠지면 Android 하나 때문에
짊어질 짐이 아니다.

**2. RN은 "웹 자산 재사용"이 아니다.** React 컴포넌트를 RN 컴포넌트로 다시 짜야
하므로 웹 화면을 그대로 담을 수 없다. §4의 재사용 전략과 방향이 맞지 않는다 —
셸에 담을 수 있는 것은 웹 화면이지 RN 화면이 아니다.

**3. 딸린 판단 — Nitro Modules도 출구가 아니었다.** 네이티브 브릿지의 최신 경로에도
Swift 쪽에 컴파일러 크래시·codegen 버그·Swift 6 strict concurrency 미지원이 열려
있었다(2026-07 확인). 애초에 선택지가 아니었다.

## 잃은 것과 재검토 조건

**잃은 것** — iOS와 Android가 UI 코드를 공유할 길. Android의 화면 품질은 웹 자산의
품질에 묶인다.

**재검토 조건** — 달력에 걸린 조건은 없다. 이 탈락은 전제 둘(목표 포지션 · 웹 자산
재사용 전략) 위에 서 있고, 전제가 서 있는 한 유효하다.
